# Design

## Context

The fork already maintains its own documentation: 12 markdown pages in `packages/@biorate/hygen/docs/`, rewritten for fork semantics (composition, glob batch actions, transforms, conditional `skip:`, interactive picker). Upstream hygen ships its site as a Docusaurus v2 app in the `hygen.io/` directory (see proposal.md for motivation). Constraints:

- Root `docs/` in the monorepo is generated TypeDoc output — must not be touched or reused.
- No pnpm workspace entry is wanted for the site; the package is published to npm with a `files` allowlist that must stay clean.
- Hosting is the user's own server (static files behind nginx); no deploy CI exists or is wanted.
- Fork features currently live inside `templates.md`, `extensibility.md`, `generators.md` as sections; they need dedicated pages.

## Goals / Non-Goals

**Goals:**

- A Docusaurus 3.x site whose docs content is the existing `docs/` directory (single source of truth).
- Dedicated fork-feature pages with clean content split from existing pages.
- Expanded landing page with fork positioning and attribution.
- Build that runs standalone inside `packages/@biorate/hygen/site/` without touching the rest of the monorepo.

**Non-Goals:**

- Deployment automation (CI workflow, rsync scripts) — the owner deploys manually.
- Search hosting/algolia setup, i18n, versioning.
- Any change to generator runtime behavior or to the `hygen-generator` spec.

## Decisions

### D1: Fresh Docusaurus 3.x scaffold, not a copy of upstream's tree

Upstream's `hygen.io/` runs Docusaurus 2.x with its own lockfile/catalog. We create a new site with current Docusaurus 3.x and reuse only ideas: config shape, the three-group sidebar, the landing page layout. Alternative (copy upstream directory and upgrade in place) rejected: dragging old lockfiles and upstream-specific config through an upgrade is more work than starting clean, and upstream's docs content would all be deleted anyway.

### D2: Content wiring via the preset's docs path

`docusaurus.config.js` presets `[[classic]]` with `docs: { path: '../docs', routeBasePath: 'docs', sidebarPath: './sidebar.js' }`. Content stays in `packages/@biorate/hygen/docs/`; nothing is copied into `site/`. Alternative (symlinks or a build-step copy) rejected: the preset path option is the supported mechanism and works with `docusaurus build` out of the box.

### D3: Content split rule — move text, leave a stub + link

When a fork feature gets its own page, the full text moves there; the source page (`templates.md` / `extensibility.md` / `generators.md`) keeps a one-paragraph summary linking to the dedicated page. This avoids duplicated content drifting apart (we just went through 4 features where docs edits happened in parallel). Cross-page links inside `docs/` use relative markdown links (`./glob-batch`), which Docusaurus resolves between docs pages.

### D4: Sidebar as static `sidebar.js` (plain object)

Explicit page lists per group, mirroring upstream's shape. Alternative (`autogenerated` from frontmatter) rejected: we want exact ordering and grouping control, and the page set is small and stable.

### D5: Landing page as a TypeScript React page (`src/pages/index.tsx`)

Expanded version of upstream's `src/pages/index.js`: hero, code examples adapted to fork semantics (glob batch, transforms, skip, picker), a fork-features section, an "differences from upstream" section mirroring the README's Differences block, npm link to `@biorate/hygen`, and attribution of jondot/hygen (MIT) in the footer/theme config. Attribution also set in `docusaurus.config.js` `footer`.

### D6: Placeholder `url`/`baseUrl`

`url: 'https://example.com'`, `baseUrl: '/'` as defaults; the owner sets real values at deploy time. Build works with placeholders (asset paths are consistent). Alternative (ask for the host now) rejected: not blocking for the change; the config exposes the two fields clearly with a comment.

### D7: Site as a self-contained npm project, invisible to publishing

`site/` has its own `package.json` (Docusaurus deps), its own `.gitignore` for `build/` and `node_modules/`, and is NOT listed in the root `pnpm-workspace.yaml` patterns... — in fact the workspace patterns `packages/*/*` DO match `packages/@biorate/hygen/site`, so to keep pnpm from treating it as a workspace package we name its private package clearly (`hygen-docs-site`, `"private": true`) and let it be a workspace package; it is never published (private), and `packages/@biorate/hygen/package.json` `files` does not include `site`. Root scripts do not build the site; building is a manual step inside `site/` (`pnpm install && pnpm build` there) documented in `site/README.md`.

## Risks / Trade-offs

- [Relative docs links in the 12 existing pages may break under Docusaurus link resolution] → during the content split, walk all cross-page links and anchors; Docusaurus build warns on dead docs links — treat warnings as errors (`onBrokenLinks: 'throw'`) so the build catches them.
- [pnpm workspace picks up `site/` and hoists deps] → acceptable: the site is `private: true`, so it can never be published; root `pnpm install` may install its deps, which is harmless. If it causes friction, a `pnpm-workspace.yaml` exclude can be added later.
- [Fork docs include fork-only config flags that may confuse readers arriving from upstream links] → landing "differences from upstream" section plus FAQ covers the deltas.
- [Docusaurus 3.x requires Node >= 18] → consistent with the monorepo `engines`; verified at build time.

## Migration Plan

Not applicable (additive feature). Rollback = delete `site/` and revert the three edited docs pages; nothing else in the repo depends on the site.

## Open Questions

None. `url`/`baseUrl` final values are deferred by design (owner sets them at deploy).

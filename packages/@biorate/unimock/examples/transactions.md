# Мокирование транзакций (Sequelize и другие connection-based API)

Полный разбор того, как транзакции попадают в снапшот, почему они ломают FIFO-реплей
без меток, и как это решается в реальном проекте (family-tree: NestJS + Sequelize).

## Как транзакция попадает в снапшот

Если коннектор замокан через `@Mockable()`, то `connector.connection('main')` возвращает
не реальный инстанс Sequelize, а **MockHandler** (Proxy) с refId `ref_Sequelize_1`.
Вызов `.transaction(options, cb)` на нём записывается как одна запись:

```jsonc
// SequelizeConnector.unimock.snap (реальный пример)
{ "_t": "c",
  "key": "call:ref_Sequelize_1:transaction:ada85d28",
  "call": {
    "args": [],              // стрипнуты через UNIMOCK_SKIP_PROXY_ARGS=1
    "result": { ... }        // сериализованный РЕЗУЛЬТАТ КОЛБЭКА
  } }
```

Три ключевых факта:

1. **Колбэк в хеше — константа** (`'<callback>'`): его тело не сериализуется, а сам колбэк
   в replay **не вызывается**. Транзакция реплеится атомарно — из снапшота возвращается
   записанный результат колбэка.
2. **Вложенные вызовы моделей внутри транзакции не реплеятся отдельно** — вся транзакция
   сворачивается в одну запись «вызов → результат колбэка».
3. **Хеш считается по сырым аргументам ДО стрипа**: опция-метка (см. ниже) влияет на ключ,
   даже если записанные `args` пустые.

## Проблема: все транзакции в одном FIFO

Без различий в аргументах все вызовы `.transaction(...)` за весь прогон дают **одинаковый
ключ** (колбэк нормализуется в константу): `call:ref_Sequelize_1:transaction:<константа>`.
Все транзакции всех спеков выстраиваются в один глобальный FIFO-катч:

- replay consume-ит записи по порядку: первая транзакция реплея получает первую записанную,
  вторая — вторую и т.д.;
- любое расхождение порядка (новая спека, условная ветка, перестановка) **сдвигает всю
  очередь**;
- исчерпанный катч не бросает ошибку, а деградирует до last-wins с `console.warn` — то есть
  транзакция `user:create` может **молча получить** записанный результат транзакции
  `person:create` (объект персоны вместо пользователя).

## Решение: уникальная метка на каждый call-site

Добавьте в опции транзакции уникальную метку — она попадёт в хеш, и у каждого сайта вызова
будет **свой** FIFO-катч:

```ts
// src/.../person.repository.adapter.ts
return this.sequelize.connection('main').transaction(
  { flow: 'person:create' } as never, // метка только для unimock; Sequelize её игнорирует
  async (t) => {
    const row = await PersonModel.create(input, { transaction: t });
    return this.toDomain(row);
  },
);
```

Эффекты:

- 19 сайтов вызова транзакций → 19 разных ключей в снапшоте
  (`transaction:ada85d28`, `transaction:4566135e`, ...);
- перемежение (interleaving) разных транзакций больше не важно — реплею достаточно,
  чтобы **каждый сайт вызывался столько же раз, сколько записан**;
- опция не раздувает снапшот: при `UNIMOCK_SKIP_PROXY_ARGS=1` записанные `args` пустые,
  а метка живёт только в хеше ключа.

`as never` — осознанный компромисс: опция не входит в публичный API Sequelize, каст
типов «притворяется», что она легальна. Чистые альтернативы — ниже.

## Правила меток

- [ ] **Уникальность по всему кодовой базе**: два сайта с одной меткой снова слипнутся в
      общий FIFO. Конвенция: `<сущность>:<операция>` (`person:create`, `user:set-telegram-link`).
- [ ] **Число вызовов сайта** в record и replay должно совпадать (иначе — last-wins деградация
      с warning).
- [ ] Метки — это **тестовая озабоченность в prod-коде**: документируйте их (AGENTS.md
      приложения), иначе их удалят при рефакторинге и реплей молча сломается.

## Фрагменты снапшота до/после

Без меток — один ключ на все транзакции:

```jsonc
{"_t":"c","key":"call:ref_Sequelize_1:transaction:00000000", ...}  // транзакция №1
{"_t":"c","key":"call:ref_Sequelize_1:transaction:00000000", ...}  // транзакция №2 — тот же ключ!
```

С метками — по ключу на сайт (реальное распределение из family-tree):

```text
18 × transaction:ada85d28   (один сайт, 18 вызовов — FIFO в пределах сайта)
14 × transaction:a3e41a03
11 × transaction:87aa88b2
10 × transaction:4566135e
...
```

## Cleaner alternatives (roadmap)

Текущий паттерн рабочий, но не идеален. Идеи для первоклассной поддержки в unimock:

1. **Опция `@Mockable({ transactionFlow: 'keyOf' })`** — библиотека сама читает метку
   из опций, стрипает её из сериализованных args и пишет в отдельное поле снапшота.
   Prod-код остаётся с меткой, но без вранья типам.
2. **Автолейблинг в тестовых моках**: тестовый `@Mockable`-подкласс переопределяет
   `transaction()` и подставляет метку из site-контекста (например, через
   `Error.captureStackTrace`) — prod-код вообще без меток, но решение магическое.
3. **Scope-реплей транзакций**: реплеить не «вызов → результат», а область с вложенными
   вызовами (transaction как scope) — правильнее всего семантически, дороже всего в реализации.
4. **Линт уникальности меток**: скрипт, проверяющий, что каждая метка встречается в одном
   call-site (защита от слипания).

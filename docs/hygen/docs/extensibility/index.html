Extensibility

hygen is extensible via a project config file (helpers, logger, template location, shell executor) and, programmatically, via the embeddable runner() API.

Project config file​

hygen looks for a config file by walking up the directory tree from where you run hygen, stopping at the first directory that contains any candidate file.

File names and priority​

The runner checks the candidates in each directory in this order:

PriorityFile nameNotes
1.hygen.jsFollows the host project's type field
2.hygen.cjsExplicit CommonJS
3.hygen.mjsExplicit ESM
4.hygen.tsTypeScript, transpiled on the fly

Nearest directory wins​

The walk goes from the current directory up to the filesystem root, and the first directory containing any candidate is used; within that directory, the priority order decides between candidates. This means:

  • You can set up a single file per project.
  • Sub-projects can override behavior with their own file.
  • You can drop one in your directory for a global default.

When candidates exist in several directories on the way up, only the nearest one is loaded and the rest are ignored — for example a .hygen.cjs in a subdirectory beats a .hygen.js higher up.

Module systems​

The resolved file is loaded with a dynamic import(), so module-system semantics follow the file extension for the explicit formats:

  • .hygen.cjs is CommonJS (module.exports).
  • .hygen.mjs is ESM (export default / named export).
  • A plain .hygen.js follows the host project's module system — the nearest package.json type field. In a "type": "module" project a .hygen.js written with module.exports will fail, so use .hygen.cjs there instead.

These explicit formats work independently of the host project's type field.

TypeScript​

.hygen.ts files are transpiled on the fly: the runner lazily registers ts-node/register/transpile-only on first use, so ts-node must be available (install it with npm i -D ts-node if it is not already a dependency).

Export shapes: named exports, default object, default class​

The resolved file's export is normalized as follows:

  1. Named exports take priority. export const templates = '_templates' merges as today. If a file mixes named fields and a default export, the named fields win. Module-interop keys emitted by transpilers (__esModule) are never treated as named exports — a default export is still resolved when only the interop key accompanies it.
  2. export default { ... } — a plain object is used as-is.
  3. export default class Config { ... } — the class is instantiated with no constructor arguments. A class extending the exported HygenConfig base class is resolved through the base class conversion (fields plus bound prototype hook methods and the configured helpers member). The base class is detected structurally — by the presence of a toRunnerConfig() method — not with instanceof, so the config still resolves correctly when the project imports a different copy of @biorate/hygen than the one the running CLI uses. Any other class is resolved to the instance's own enumerable properties — prototype methods and getters are not read, and class methods never become helpers. A constructor that requires arguments (or throws) fails the run with a standardized error naming the config file.

The class form is typed with the ProjectConfig interface exported from the package (templates, argCase, helpers, hooks — a compile-time contract only):

// .hygen.ts
import type { ProjectConfig } from '@biorate/hygen';

export default class Config implements ProjectConfig {
  templates = '_templates';
  helpers = {
    slug: (s: string) => s.toLowerCase().replace(/\s+/g, '-'),
  };
  hooks = {
    async beforeAll(ctx) {
      ctx.logger.log(`run starting in ${ctx.cwd}`);
    },
  };
}

Because only own enumerable properties are read, cache expensive helpers in an own field (not a prototype getter):

export default class Config {
  helpers = this.#build();
  #build() {
    return {
      /* expensive helper setup */
    };
  }
}

Accessing run arguments from class helpers​

A static helpers object cannot see run arguments. To derive helpers from them, make the helpers field a factory — the same function form as in the object config. It is invoked per render with the run's locals (positionals under _, CLI flags, name, prompt answers):

import type { Helpers, ProjectConfig, RunnerContextConfig } from '@biorate/hygen';

export default class Config implements ProjectConfig {
  // note the explicit annotations: TypeScript does not contextually type
  // class property initializers from `implements`
  helpers = (locals: Record<string, unknown>, config: RunnerContextConfig): Helpers => ({
    slug: () =>
      String(locals.name ?? '')
        .toLowerCase()
        .replace(/\s+/g, '-'),
  });
}

Own properties outside the ProjectConfig key set (templates, argCase, helpers, hooks) are ignored with a warning naming the property (non-base class configs only).

The HygenConfig base class​

For a full-featured class experience, extend the abstract HygenConfig class exported from the package: state lives in constructor-initialized fields and lifecycle hooks are prototype methods with a live this — no nested hooks: { ... } object required:

// .hygen.ts
import { HygenConfig } from '@biorate/hygen';

export default class Config extends HygenConfig {
  private count = 0;

  constructor() {
    super(); // initializes neutral defaults: templates/localsDefaults/helpers unset, argCase = 'keep'
    this.templates = '_templates';
  }

  // helpers in any of three forms: property, getter, or factory method
  // (the method IS the factory form: invoked per render with (locals, config),
  //  bound so `this` is the config instance)
  helpers() {
    return { slug: (s: string) => s.toLowerCase().replace(/\s+/g, '-') };
  }

  // hooks as prototype methods; `this` carries state across pairs
  beforeEach(ctx) {
    this.count += 1;
    ctx.logger.log(`pair #${this.count}`);
  }
  afterEach(ctx, results) {
    /* results is the pair's ActionResult[] */
  }
}

Notes:

  • Constructor defaults. super() initializes templates, localsDefaults and helpers as undefined and argCase as 'keep' — override them in the subclass constructor or as fields.
  • The templates field is cwd-relative. A relative templates value from the project config is resolved against the run's cwd (the same way the default _templates folder is), so this.templates = '_tpl' points at <cwd>/_tpl. Absolute paths and non-existent values are kept as-is.
  • Three helpers forms. Own property map, getter, or factory method — all resolve. An own property shadows a prototype method (standard TypeScript semantics); use one form per class.
  • Only overridden hooks are registered. The base's no-op hook methods are omitted from the effective config, so a subclass that overrides, say, only beforeEach behaves exactly like an object config declaring a single hook.
  • Internal state stays internal. Extra fields on a HygenConfig subclass (caches, counters) never leak into the runner configuration and emit no unknown-property warning — unlike non-base class configs, where unknown own properties warn.
  • No transport fields. logger, exec, cwd and createPrompter remain programmatic runner-construction concerns and are not part of the base class.

Backward compatibility​

Projects with an existing .hygen.js keep resolving exactly as before — it remains the highest priority candidate.

Project lifecycle hooks​

The config file may declare an optional hooks field: a plain object with the four lifecycle methods beforeAll, beforeEach, afterEach, afterAll. Project hooks apply to every generator run, wrapping whatever the action-level hooks do (see Ordering and composition):

// .hygen.js
module.exports = {
  helpers: {
    /* ... */
  },
  hooks: {
    async beforeAll(ctx) {
      ctx.logger.log(`run starting in ${ctx.cwd}`);
    },
    async beforeEach(ctx) {
      // runs before each (name, action) pair's prompt phase
    },
    async afterEach(ctx, results) {
      // results is the pair's ActionResult[]
    },
    async afterAll(ctx, results) {
      // results accumulates all pair results of the run
    },
  },
};

Key points:

  • Project hooks are a plain object, a plain field, or base-class methods. Unlike action hooks (a class, see The hooks class), the project-level hooks is a plain object with the same four methods (or a hooks field on a legacy class-based config), or — for configs extending HygenConfig — simply overridden prototype methods (beforeEach(ctx) { ... }). There is no prompt section at this level.
  • State via closure or instance fields. A plain object holds state in the config module's closure; a HygenConfig subclass keeps it in instance fields readable through this in every hook.
  • Lenient validation. Only function-valued entries are used; unknown or non-function entries are ignored with a warning instead of failing the run.
  • Run-scoped methods (beforeAll, afterAll) are called once per run and receive action: '*' with no name.
  • All methods are optional and may be async.

Action hooks and lifecycle​

An action folder can carry a hook module that both prompts and observes the run through lifecycle methods.

Where action hooks live​

The runner checks the candidates in the action folder in this order; the first existing file wins and nothing else is loaded:

PriorityFile nameNotes
1hooks.tsModern form — TypeScript, on-the-fly
2hooks.jsModern form — follows host project type
3hooks.mjsModern form — explicit ESM
4hooks.cjsModern form — explicit CommonJS
5index.jsLegacy prompt hook
6index.tsLegacy prompt hook
7prompt.cjsLegacy prompt hook
8prompt.jsLegacy prompt hook
9prompt.tsLegacy prompt hook
  • The four hooks.* files always take priority over the legacy files.
  • Legacy modules (index.*, prompt.*) keep working unchanged and have no lifecycle methods — they only prompt (see prompt hooks).
  • Hook files are not rendered as templates; they are loaded as modules.

The hooks class​

A hooks.* file must export a class as its default export; otherwise a HookModuleError naming the file is thrown. The runner constructs one instance per action run and reuses it for every (name, action) pair, so instance fields carry state across pairs.

All methods are optional and may be async:

MethodCalled
beforeAll(ctx)Once per action run, before that action's pairs
beforeEach(ctx)Before the pair's prompt phase
afterEach(ctx, results)After the pair's execution; results is that pair's ActionResult[]
afterAll(ctx, results)Once per action run; results accumulates all of the action's pair results
prompt({ prompter, args, h })The prompt section — replaces the legacy prompt hook

The ctx object passed to the lifecycle methods:

FieldDescription
cwdWorking directory of the run
templatesResolved templates directory
generatorGenerator name (e.g. mailer)
actionAction name (new, or new:subaction) — '*' for run-scoped hooks
subactionSubaction, when present
nameCurrent name expansion, when present
argsCLI flags plus name, before prompt answers
hHelpers (built-in + project), resolved once per run from CLI args on first read
loggerThe run's logger
drytrue in --dry runs

Run-scoped hooks (project.beforeAll, project.afterAll) receive action: '*' and no name.

The prompt section​

The prompt({ prompter, args, h }) method is the prompt phase of the class — it replaces the legacy prompt hook, and its returned object becomes template variables. The h namespace is resolved lazily on first read from the run's CLI arguments (positionals plus flags). Everything documented on the prompt hooks page (prompter usage, filtering, args) applies.

Declarative parameters (params)​

A class-based hook module can also declare a parameter schema — a params array on the hooks class — that drives flag coercion, prompting and validation for the action, replacing hand-written prompt questions with one declaration. The uniform form is an instance field — the same declaration style as the project config class (see Global parameters below), and the descriptors may be computed in the constructor or reference instance state:

// hooks.ts
export default class Hooks {
  params = [
    { name: 'label', type: 'string', required: true, message: 'Component name?' },
    { name: 'count', type: 'number', default: 1 },
    { name: 'dry', type: 'boolean' },
    { name: 'stamp', type: (raw) => new Date(raw ?? Date.now()) }, // custom type
  ];

  beforeAll(ctx) {
    /* ... */
  }
}

The legacy static params member is still honored for backwards compatibility; when both forms exist, the instance field wins and the run logs a warning naming both declaration forms.

Per (name, action) pair the engine:

  1. Coerces each declared parameter found among the CLI flags to its type ('3' → 3 for number, 'true' → true for boolean). A value that cannot be coerced fails the run naming the parameter and the expected type.
  2. Prompts once for every required parameter that was not supplied as a flag (message is the question text, default the initial answer). Parameters already supplied are never asked again.
  3. Validates the merged values against the declared types; a required parameter that stayed absent — or whose value is empty or whitespace-only, from a flag (--param="") or a prompt — fails the run naming the parameter.

Empty answers on required parameters. In an interactive terminal an empty Enter on a required string/number question does not end the run: the question is re-asked in place with a Field "<name>" is required warning until a non-empty answer is given; the re-asked question keeps its message and default. A required boolean is never re-asked — the answered or default value is accepted as-is (an empty confirm answer resolves to false). Non-required parameters accept empty values unchanged.

Interaction with argCase. Under argCase: 'upper-underscore' flag keys arrive normalized (--root /x becomes ROOT), so the schema resolves each descriptor's value under the normalized alias of its name too — declare the parameter as root and the supplied flag is found. The resolved value is exposed to templates and hooks under both the declared name and the normalized alias (root and ROOT), whichever path (flag or prompt) supplied it.

type accepts 'string' (default), 'number', 'boolean' — or a function whose return value becomes the parameter value (a thrown error surfaces under the parameter name). An unknown string type fails when the hooks are loaded, so a schema mistake never reaches a run. Only the modern class form (hooks.*, kind class) honors the params schema — declared as an instance field (uniform with the project config) or, for backwards compatibility, as a legacy static params member; legacy modules keep their own params(...) function.

Global parameters (project config)​

A parameter needed by every generator can be declared once in the project configuration (.hygen.*, including a HygenConfig subclass) as a params array — the same descriptor shape as the action's params field:

// .hygen.ts
export default {
  params: [{ name: 'root', type: 'string', required: true }],
};

Global parameters are coerced from CLI flags and prompted once per run, before any pair (and any lifecycle hook) runs; the resolved values join the base arguments, so every pair's templates and hooks see them and action-level prompts never re-ask them. All parameter rules apply unchanged (coercion, required empty-value rejection with the interactive re-ask, argCase alias resolution). When an action's params field declares the same name, the action-level descriptor wins for that action and the run logs a warning naming the parameter and both declaration levels.

Flag-key normalization (argCase)​

By default flag keys keep their CLI spelling: --my-flag reaches templates as the my-flag local. When the runner configuration declares argCase: 'upper-underscore', hyphenated and camel-cased flag keys are normalized to UPPER_UNDERSCORE (--my-flag and --myFlag both become MY_FLAG). The reserved keys (_, ts, name, generator, action) are never normalized.

Ordering and composition​

Project hooks wrap action hooks like nested test suites:

project.beforeAll
  action.beforeAll
    for each (name, action) pair:
      project.beforeEach
      action.beforeEach
      prompt -> render -> execute
      action.afterEach(results)
      project.afterEach(results)
  action.afterAll
project.afterAll

project.beforeAll/afterAll run once per run; the action-level ones run once per action run. beforeEach runs before the prompt phase; afterEach runs after execution.

Because the class instance persists across pairs, instance fields make per-run state trivial — for example a counter that increments per pair:

// _templates/mailer/new/hooks.ts
export default class Hooks {
  private n = 0;

  async beforeEach(ctx) {
    this.n += 1;
    ctx.logger.log(`pair #${this.n}`);
  }
}

With hygen mailer new a,b the two name expansions see 1 then 2.

Failure semantics​

Hook that throwsEffect
beforeAllEvery pair it guards is skipped and marked failed with the hook error; its matching afterAll still runs. A project beforeAll failure guards all pairs; an action beforeAll failure guards only that action's pairs.
beforeEachThat pair is skipped and marked failed; both afterEach levels still run for it.
afterEachThe pair is recorded as failed; the run fails.
afterAllThe run fails even when every pair succeeded.

Pair-attributable failures (beforeEach, afterEach) are reported with the pair's action and name in failures/statuses. Run-scoped failures (afterAll, and beforeAll with no pair to guard) use the sentinel action: '*' with no name.

A single-pair × single-action run rethrows the original hook error unchanged. Without --keep-going the run fails with the pair label; with --keep-going hook failures are collected per pair and the remaining pairs still run.

Dry mode​

In --dry runs hooks are called exactly as usual and receive ctx.dry === true; no files are written. A hook can use ctx.dry to skip its own side effects.

Helpers​

Add functions to the h helper namespace from .hygen.js. A template that uses a function called extended:

---
to: given/hygen-js/new.md
---
this demonstrates hygen loaded up .hygen.js and extended helpers.
<%= h.extended('hello') %>

Define it in a project-root .hygen.js:

module.exports = {
  helpers: {
    extended: (s) => s.toUpperCase(),
  },
};

Beyond inlining a utility, you can require any code in your project and export it for hygen to use.

External libraries as helpers​

Anything require-able in the project where you run hygen can be exposed to templates the same way — utility libraries, sibling packages in a monorepo, your own modules.

Note: the library must be an installed dependency of the project where hygen runs. hygen resolves require from the running project, not from its own bundle — a library that is not installed there will fail to load.

Lodash (plain object form)​

Require the library at config load and bind it (whole or in wrappers) under a namespace:

// .hygen.js
const _ = require('lodash');

module.exports = {
  helpers: {
    _: _,
    slug: (s) => _.kebabCase(s),
  },
};

Use it in a template as h.<namespace>:

---
to: given/hygen-js/libraries.md
---
<%= h._.capitalize(name) %>
<%= h.slug(name) %>

Sibling @biorate/* package (monorepo usage)​

The same mechanism works for sibling packages in the monorepo, as long as the running project depends on them:

// .hygen.js
const { changeCase } = require('@biorate/change-case');

module.exports = {
  helpers: { changeCase },
};
<%= h.changeCase.paramCase(name) %>

Function form (lazy resolution with a friendly error)​

helpers can also be a function (locals, config) => Helpers. It is invoked for every template render — once for the frontmatter attributes and once for the body — with that action's locals (name, flags and prompt answers included), and lazily at most once per run when lifecycle hooks or a class prompt section read h. A hook-scoped call receives the run's CLI arguments (_ positionals plus flags, without the per-pair name and without prompt answers).

Because the same factory can be called several times in one run, it must be re-entrant and must not depend on per-template or prompt-provided values: locals is the raw argument object of that particular call, not a stable per-run store. Outside rendering the runner never calls the factory with empty locals.

This is the place for lazy resolution: wrap the require in try/catch and throw a friendly error instead of the raw Cannot find module:

// .hygen.js
module.exports = {
  helpers: (locals, config) => {
    let _;
    try {
      _ = require('lodash');
    } catch (e) {
      throw new Error(
        `lodash is required by this generator's config — install it: npm i -D lodash`,
      );
    }
    return {
      _: _,
      slug: (s) => _.kebabCase(s),
    };
  },
};

Content transforms​

Besides helpers, the config file can declare a transforms namespace: named post-processors that run over the rendered template content before it is written or injected. Each transform is a function (content, locals) => string | Promise<string>; a template opts in with the transform: frontmatter attribute, and several transforms can be chained left-to-right with |.

See Content transforms for the full reference — the config shape, chaining, and the failure/edge modes.

Customizing logger, template location and shell executor​

The same .hygen.js file can customize the logger, the templates folder, and the shell executor:

const path = require('path');

module.exports = {
  templates: `${__dirname}/_templates`,
  logger: {
    ok: (msg) => process.stdout.write(msg),
    notice: (msg) => process.stdout.write(msg),
    warn: (msg) => process.stderr.write(msg),
    err: (msg) => process.stderr.write(msg),
    log: (msg) => process.stdout.write(msg),
    colorful: (msg) => process.stdout.write(msg),
  },
  exec: (sh, body) => {
    console.log(`[dry exec] ${sh}`);
  },
};

Embeddable runner() API​

The same pipeline the CLI uses is available programmatically as runner(argv, config) from the package entry point. It is useful for building your own binary, test harness, or tool over hygen:

import { runner } from '@biorate/hygen';
import * as path from 'path';

async function main() {
  const result = await runner(['mailer', 'new', 'autumn-newsletter'], {
    cwd: process.cwd(),
    templates: path.join(process.cwd(), 'templates'),
    logger: {
      ok: (msg: string) => console.log(msg),
      notice: (msg: string) => console.log(msg),
      warn: (msg: string) => console.warn(msg),
      err: (msg: string) => console.error(msg),
      log: (msg: string) => console.log(msg),
      colorful: (msg: string) => console.log(msg),
      // optional; message output falls back to `colorful` when absent
      colorfulHeader: (header: string, body: string) =>
        console.log(`\x1b[1m${header}\x1b[0m:\n${body}`),
    },
    createPrompter: <Q, T>() => ({
      prompt: async (_arg0: Q) => ({} as T),
    }),
    exec: (sh: string, body: string) => {
      void sh;
      void body;
    },
  });

  if (!result.success) {
    console.error(result.failure?.message);
    process.exit(1);
  }
}

void main();

RunnerConfig requires cwd, logger (a Logger-shaped object), createPrompter, and exec. Everything else — templates, templatesOverride, helpers, localsDefaults, debug — is optional. The result (RunnerResult) exposes success, time, actions, and a failure block when the run fails.

For the full API reference see the typedoc.
